# Project Progress — Procurement MVP

## Overview (what's implemented)

- **PO Service**: Full business logic for Purchase Orders in `backend/src/services/purchase-order-service.js` including payload validation, PO number generation, transactional creation with row-level locking, allocation records, and submit transition.
- **PO Routes**: REST endpoints implemented in `backend/src/routes/purchase-order-routes.js`.
- **Tests**: Focused Jest unit tests for PO service and routes covering validation, over-allocation guard, transactional behavior, and status transitions. See `backend/tests/services/purchase-order-service.test.js` and `backend/tests/routes/purchase-order-routes.test.js`.

## Purchase Order API Endpoints (available)
- `GET /api/purchase-orders` — list PO headers (mapped header fields).
- `POST /api/purchase-orders` — create a new PO (validates payload; enforces allocation qty <= PR line remaining via transactional locks). Returns `201` and PO detail on success; `422` on validation/guard errors.
- `POST /api/purchase-orders/:id/submit` — submit a DRAFT PO (changes status to `SUBMITTED`). Returns `422` if PO not in `DRAFT`.
- `GET /api/purchase-orders/:id` — get PO header + lines + allocations (404 if not found).
- `GET /api/purchase-orders/:id/open-lines` — get PO info and only lines that are open for GR (qtyOpenForGr > 0). 404 if PO not found.

## Key implementation notes
- Validation logic lives in `backend/src/services/purchase-order-service.js` (function `validateCreatePayload`).
- Over-allocation guard: each referenced PR line is `SELECT ... FOR UPDATE` to prevent concurrent allocation; creation rolls back on errors.
- PO numbers generated by `createPoNumber()` (pattern `PO-2026-XXXX`).
- Submit enforces only `DRAFT` → `SUBMITTED` transition.
